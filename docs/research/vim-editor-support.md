# Vim editing in OpenTUI and OpenCode V2

Checked 27 September 2026. This note concerns the snippets plugin's own OpenTUI textarea, with `@opentui/core`, `@opentui/solid`, and `@opentui/keymap` 0.5.10, `@opencode/plugin` 2.0.12, and a host last tested at 2.0.17.

## Finding

There is no ready Vim editor mode to turn on for a plugin-owned textarea in those dependencies. OpenTUI supplies cursor, word, selection, undo, and delete operations, plus a keymap capable of sequences and input modes. It does not supply the Vim state machine and commands. OpenCode V2's CLI plugin API lets a plugin add focused keymap layers, but does not expose a reusable Vim editor or its external-editor function. The community implementation below targets OpenCode's prompt and would need adaptation for the snippets textarea. No supported reusable engine API was identified. [OpenTUI 0.5.10 textarea actions and defaults](https://github.com/anomalyco/opentui/blob/v0.5.10/packages/core/src/renderables/Textarea.ts#L17-L137), [OpenTUI keymap guide](https://github.com/anomalyco/opentui/blob/v0.5.10/packages/keymap/README.md), [OpenCode V2 CLI plugin API](https://opencode.ai/v2/docs/build/plugins/cli).

## What the published OpenTUI packages provide

- The 0.5.10 [`TextareaRenderable`](https://github.com/anomalyco/opentui/blob/v0.5.10/packages/core/src/renderables/Textarea.ts#L17-L137) declares fixed actions such as `move-left`, `word-forward`, `delete-line`, and `undo`. Its [`keyBindings` mapping and `handleKeyPress`](https://github.com/anomalyco/opentui/blob/v0.5.10/packages/core/src/renderables/Textarea.ts#L135-L285) map a key to one action and insert ordinary printable input. Word movement and deletion are implemented on the [edit buffer renderable](https://github.com/anomalyco/opentui/blob/v0.5.10/packages/core/src/renderables/EditBufferRenderable.ts#L913-L971). A mapping such as `h` to `move-left` alone would insert `h` in other circumstances and would not provide insert/normal modes, operator-pending commands such as `dw`, counts, registers, or Vim word rules.
- [`@opentui/keymap`](https://github.com/anomalyco/opentui/blob/v0.5.10/packages/keymap/README.md) supplies focus-scoped layers, multi-key sequences, state, and interceptors. The [OpenTUI adapter's edit-buffer commands](https://github.com/anomalyco/opentui/blob/v0.5.10/packages/keymap/src/addons/opentui/edit-buffer-bindings.ts) bind existing textarea actions. [`registerNeovimDisambiguation`](https://github.com/anomalyco/opentui/blob/v0.5.10/packages/keymap/src/addons/universal/neovim-disambiguation.ts) handles only the timeout between an exact binding and its possible continuation, such as `g` and `gg`. It does not implement Vim editing. The package's test references to `vim.mode` use a sample key for the generic keymap, not a shipped Vim mode. [Keymap state test](https://github.com/anomalyco/opentui/blob/v0.5.10/packages/keymap/src/tests/keymap.sequences-and-state.test.ts).
- The official OpenTUI repository is [`anomalyco/opentui`](https://github.com/anomalyco/opentui). Its [v0.5.10 release](https://github.com/anomalyco/opentui/releases/tag/v0.5.10) was published 1 September 2026; [v0.5.12](https://github.com/anomalyco/opentui/releases/tag/v0.5.12) was the newest release found, published 22 September. Inspection of the current `main` textarea and keymap did not reveal an added Vim engine. No upstream branch name or open pull request matching Vim or modal editing was found in the GitHub branch and PR listings at the check date. These negative searches cannot rule out unpublished work or a differently named branch.

## OpenCode proposals and Dax's comment

The official OpenCode repository is [`anomalyco/opencode`](https://github.com/anomalyco/opencode); `sst/opencode` redirects there. The V2 `dev` tree's [prompt component](https://github.com/anomalyco/opencode/blob/b471c2b4495747353af768fbf2e0790c9d820ce2/packages/tui/src/component/prompt/index.tsx#L1369-L1439) uses an OpenTUI textarea, while its `normal`/`shell` modes concern the prompt's shell input, not Vim. A repository search found no Vim editor module in `packages/tui` or the V2 CLI plugin implementation. The [V2 CLI guide](https://opencode.ai/v2/docs/build/plugins/cli#commands-and-keymaps) shows how plugins can register bindings in layers for specific renderables and temporary input modes. It does not document a Vim editor API.

## Community implementation and reuse limit

The author of #12679 published [`@leohenon/opencode-vim-plugin`](https://github.com/leohenon/opencode-vim-plugin/blob/main/README.md), which implements prompt Vim editing and has [shared state, motion, and handler modules](https://github.com/leohenon/opencode-vim-plugin/tree/main/src/vim). Its [package manifest](https://github.com/leohenon/opencode-vim-plugin/blob/main/package.json) declares version 0.1.6, OpenCode `>=1.17.10`, `@opencode-ai/plugin` `>=1.17.10`, and OpenTUI `>=0.4.2`; exports are only `.` and `./tui`, both pointing to the built TUI plugin. Its [prompt integration](https://github.com/leohenon/opencode-vim-plugin/blob/main/src/prompt-vim.ts) binds to OpenCode's own focused prompt and 1.x TUI API, not a caller-provided textarea or `@opencode/plugin` 2.x. The README [limits coverage to the prompt](https://github.com/leohenon/opencode-vim-plugin/blob/main/README.md#L320-L322). It is evidence that an implementation exists, but not a drop-in dependency for the snippets editor on V2. Porting or copying its motion modules would entail substantial adaptation and ownership. No V2 compatibility test or supported reusable engine entrypoint was identified.

## External editor boundary

OpenCode V2 [opens `$VISUAL` or `$EDITOR`](https://github.com/anomalyco/opencode/blob/b471c2b4495747353af768fbf2e0790c9d820ce2/packages/tui/src/editor.ts#L26-L61) by writing a temporary Markdown file, suspending the renderer, inheriting terminal I/O for the editor process, then reading the file and resuming rendering. Its [documented `<leader>e` binding](https://opencode.ai/v2/docs/cli/keybinds) targets the host's `prompt.editor`. The [CLI plugin API](https://opencode.ai/v2/docs/build/plugins/cli) does not export that `openEditor` helper for a plugin's own editor. The snippets helper uses the same environment variables and can open the actual snippet file. External editing does not bring the host prompt's completion or inline UI into the launched editor.

**Uncertainty:** This report analyzes source and API documents. It does not test the community plugin on OpenCode V2 or a plugin-owned textarea with the plugin's internal modules. No release schedule from the first-party maintainers for Vim editing was found. If an upstream V2 Vim API appears, confirm the published package exports and the exact host version before integrating it.
